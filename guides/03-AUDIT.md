# 03 — 自动审计

## 1. 审计不是“自动整理记忆”

它不是每隔 200 轮就把对话总结成一张新 A 表。

它做的是：

```text
在当前 index 里找一些可能值得看的话题簇
把它们作为候选提示交给你
```

写不写 A，仍然由这个 session 自己决定。

**比如这种情况：**

```text
如果审计提示了一个候选，但实例直接忽略，
则什么都不会改变，A 表不会自己长。
```

## 2. 为什么是 200 轮

200 轮是一个折中：

```text
太短：话题还没稳定，候选全是噪声
太长：发现得太晚，前面已经散掉
```

所以默认：

```text
每 200 轮最多触发一次
```

不是每轮都检查，也不是永不检查。

**比如这种情况：**

```text
如果 session 只有 50 轮，
则还没到第一次审计的阈值，不应该期待 [continuity:audit]。
```

## 3. 审计读什么

它读的是已经存在的索引：

```text
bc-index.jsonl 的 vec
bc-index.jsonl 的 chatter
bc-index.jsonl 的 keywords
bc-index.jsonl 的 conceptScores
```

它不重读全部原文。

所以：

```text
如果旧记录没有 vec
则审计可能无法正常做聚类
```

这也是为什么重建流程里有“补 vec”这一步。

## 4. 候选怎么来的

大致是：

```text
把带 vec 的记录做聚类
簇大小至少 10
算簇内最高概念分的平均值 topicMax
topicMax < 0.5 才算候选
按 topicMax 升序，最多 5 条
```

直觉：

```text
一个簇如果和已有 A 都不太像，
它可能是“还没被命名的新话题”
```

**比如这种情况：**

```text
如果 A 表本身是空的，
则没有概念可以算 topicMax，
审计会直接跳过。
```

这就是 500 轮没有审计提示的常见原因。

## 5. 审计结果放在哪

```text
sessions/<id>/expand-hint.jsonl       候选记录
sessions/<id>/expand-hint.pending.json 下一轮要注入的文本
sessions/<id>/audit-state.json         上次审计轮次/运行状态
```

下一轮 pre-step 会把 pending 注入成：

```text
[continuity:audit]
```

只有真的以 `role=user` 出现，才算送达。

**比如这种情况：**

```text
如果 pending 写入了，但承载消息被折叠掉，
则实例可能根本没看到这次审计。
```

## 6. 审计和 A 的关系

顺序是：

```text
A 非空 -> 审计有东西可算 -> 可能产生候选
A 空   -> 审计跳过
```

**比如这种情况：**

```text
如果 A 空，B 也空，审计也不来，
则不是三个功能同时坏了；
根因只有一个：A 没有建立。
```

## 7. 你看到审计时应该做什么

先看：

```text
turn 范围
size
topicMax
chatter
kw
```

然后：

```text
多数叙事簇是噪声 -> 跳过
确实是稳定话题 -> 才写一条 A
不确定 -> 不写
```

不要因为“审计来了”就必须加表。

## 8. 审计不替代 rebuild

审计是增量提示。

如果历史已经有 500 轮，A 还是空：

```text
审计不会替你补前 500 轮
```

这种情况应该走 `04-REBUILD.md`。

**比如这种情况：**

```text
如果 500 轮都空着，只等下一次审计，
则即使下一次审计来了，也只能看到最近的簇，
前面的历史仍然没有 A/B。
```

## 9. vec 为空

如果 A/B/C/K 有，但 vec 为空，审计同样跑不起来。
见 `06-EMBEDDING.md`。
